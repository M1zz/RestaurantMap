# 진짜 미식 — 단골 인정 · 미식 기준 · 단골 후기

이 앱이 가려는 곳과, 그 숫자와 항목이 어디서 왔는지 적어 둔다. 규칙을 바꿀 때는 여기부터 고친다.

## 방향

좋아한다고 **말한** 가게가 아니라 **자주 간** 가게를 좋아하는 가게로 인정한다.
그렇게 쌓인 후기를 나누고, 기록은 미식의 기준으로 남긴다.

세 가지가 서로 물려 있다.

1. 단골 인정: 다녀온 날을 세어 앱이 정한다. 사람이 고르지 않는다.
2. 미식 기준: 방문마다 접시 위의 음식을 네 가지로 적는다. 다섯째(한결같음)는 앱이 센다.
3. 단골 후기: 단골이 된 집에만 올릴 수 있다. 한 번 가 보고 쓴 글이 없다.

## 단골 인정 (`Models/Regular.swift`)

| 단계 | 조건 |
|---|---|
| 다시 간 집 | 서로 다른 날 2번 |
| 단골 | 서로 다른 날 4번 |
| 인생 맛집 | 단골 + 첫 방문부터 180일 넘게 이어짐 + 최근 90일 안에 다녀옴 |
| 한때 단골 | 단골이었지만 365일 넘게 가지 않음. 순위에서 빠진다 |

- 하루에 한 번만 센다. 같은 날 여러 번 적어도 방문 한 번이다.
- 나의 미슐랭은 단골 이상을 앱이 줄 세운 것이다. 단계, 다녀온 날 수, 평균 별점, 최근 방문 순이고 자리는 여섯이다.
  예전에는 Plus 사용자가 직접 여섯 곳을 고르고 순위를 적었다. 같은 순위가 둘일 수 있었고, 이 방향과 맞지 않아 걷어냈다.
  `Restaurant.isTop6` · `top6Rank` 는 저장 파일과 iCloud 틀을 지키려고 남겨 두었고 쓰지 않는다.
- 방문 기록이 없는 예전 '가본 곳'은 처음 적은 날 하루로 친다.

숫자의 근거. 업계가 공인한 단골 기준은 없다. 아래 자료에서 끌어온 설계다.

- 2번: 풀서비스 식당에서 첫 방문 뒤 다시 올 확률은 절반이 안 된다. 두 번째 방문부터가 선택이다.
- 4번: 네 번째 방문 뒤로 재방문 확률이 90% 안팎까지 오른다는 Paytronix 2017 자료("충성은 네 번째 방문에서 굳는다").
  업체 자료이고 원자료 · 표본은 확인하지 못했다.
  https://www.fsrmagazine.com/industry-news/research-loyalty-established-fourth-visit/
- 하루 한 번, 최근성: Foursquare Swarm 의 Mayor 가 하루 체크인 한 번만 세고 최근 30일을 본다.
  https://www.engadget.com/2015/06/22/swarm-foursquare-mayor/
- 블루리본 서베이의 리본 한 개가 "다시 찾아가고 싶은 곳"이다. 다시 가는 것이 인정의 첫 단계라는 생각과 같다.

## 미식 기준 (`Models/Gourmet.swift`)

미쉐린 가이드가 밝힌 다섯 기준을 따른다. 별은 접시 위의 음식만 보고 준다. 서비스 · 분위기 · 값은 보지 않는다.
https://guide.michelin.com/kr/ko/article/features/what-is-a-michelin-star-KOREAN

| 미쉐린 기준 | 앱에서 |
|---|---|
| 양질의 재료 | 재료 (1~5) |
| 요리 기술의 숙련도 | 조리 (1~5) |
| 맛의 조화 | 조화 (1~5) |
| 음식에 드러나는 셰프의 개성 | 개성 (1~5) |
| 메뉴 전체와 시간이 지나도 유지되는 일관성 | 한결같음. 묻지 않고 별점의 흔들림으로 센다 (세 번 이상 간 집) |

- 넷 다 선택이다. 적고 싶은 것만 적는다.
- 고미요도 재료 · 기술 · 개성 · 꾸준함을 본다. https://fr.gaultmillau.com/en/faq/comment-sont-classes-les-restaurants--les-toques-1-a-5-0-a-20-points
- 타베로그 · 자갓은 서비스 · 분위기 · 가성비를 따로 받는다. 이 앱은 넣지 않았다. 넣게 되면 음식 점수와 섞지 않는다.
- 음식 종류별 맛 평가(맵기 · 샤리 · 국물 …)는 그대로 있다. 그쪽은 어떤 맛인가, 이쪽은 얼마나 잘 만든 음식인가다.

## 단골 후기 (`Services/RegularReviews.swift`)

- iCloud 공개 데이터베이스(`iCloud.com.Ysoup.restaurantmap`)의 `RegularReview`. 식당 하나에 내 후기 하나.
- 공개하는 것: 가게 이름 · 주소 · 좌표, 다녀온 횟수, 몇 달째인지, 별점과 미식 기준 평균, 한결같음, 한마디, 별명.
- 공개하지 않는 것: 다녀온 날짜, 사진, 메모, 내 위치.
- 새 방문을 남기면 올려 둔 후기의 숫자를 맞춘다. 한마디는 그대로다.
- 원격 스위치 `publicReviews` 로 심사 없이 끌 수 있다(`RemoteFlags` 레코드의 Int64 필드, 0 이면 끔).

### 심사 지침 1.2 (사용자가 올린 글)

| 요구 | 앱에서 |
|---|---|
| 부적절한 내용 거르기 | `ReviewFilter` 가 올리기 전에 욕설 · 링크 · 연락처를 막는다. 사진은 받지 않는다 |
| 신고와 제때 대응 | 후기마다 신고. `ReviewReport` 레코드와 피드백함으로 온다. 신고한 글은 신고한 사람 화면에서 바로 사라지고, 서로 다른 세 사람이 신고하면 모두에게서 가려진다. 개발자는 앱에서 바로 내린다 |
| 악성 사용자 차단 | 후기마다 '이 사람 차단'. 차단도 신고로 전해진다 |
| 연락처 | 후기 규칙 화면의 이메일 |
| 약관 동의 | 처음 올릴 때 후기 규칙에 동의 |

### 운영 — 사람이 하는 일

- 신고는 24시간 안에 본다. 피드백함에 `[후기 신고: …]` 로 오고, 후기 ID 와 올린 사람 ID 가 들어 있다.
- 규칙을 어긴 글은 앱에서 내린다: 설정 ▸ 버전을 7번 눌러 마스터 모드를 켜면, 단골 후기 카드의 `…` 에
  '관리자: 모두에게서 내리기' 가 보인다. 누르면 레코드가 지워져 모든 사용자 화면에서 사라진다.
  남의 글을 지울 수 있는 것은 Moderator 역할을 받은 iCloud 계정뿐이다(아래 6번). 버튼만 보여서는 지워지지 않는다.
- 서로 다른 세 사람이 신고한 글은 앱이 먼저 모두에게서 가린다(`RegularReviews.hideAfterReports`). 글은 지워지지 않고 남으니,
  신고가 억울하면 CloudKit 콘솔 ▸ `ReviewReport` 에서 그 글의 신고 레코드를 지우면 다시 보인다.
- 같은 사람이 되풀이하면 CloudKit 콘솔 ▸ `RegularReview` 에서 `author` 로 찾아 모두 지운다.

## 무엇이 무료이고 무엇이 Plus 인가 (`Services/RestaurantPlan.swift`)

기준은 한 줄이다. **적는 것은 무료, 모아 보는 것과 꾸며 내보내는 것은 Plus.**

| | 무료 | Plus |
|---|---|---|
| 단골 인정 · 나의 미슐랭 | ○ | ○ |
| 방문마다 미식 기준 적기 · 보기 | ○ | ○ |
| 단골 후기 보기 · 올리기 | ○ | ○ |
| 미식 총평 (식당별 기준 평균 · 한결같음) | | ○ |
| 단골 카드 공유 | | ○ |

- 단골 인정과 후기를 잠그지 않는 이유: 이 앱이 무엇인지가 거기 있고, 후기는 올리는 사람이 많아야 읽을 것이 생긴다.
- 직접 고르던 탑6 가 Plus 에서 빠진 자리를 미식 총평과 단골 카드가 채운다.
- 공개 후기에는 올린 사람의 기준 평균이 실린다. 무료 사용자도 자기 후기에서는 그 숫자를 본다. 잠그는 것은 식당 화면의 총평이다.

## 배포 전에 CloudKit 에서 할 일 (사람)

스키마는 기기에서 올릴 수 없다. 아래를 하지 않으면 스토어 빌드에서 후기 화면이 '준비 중'으로 서고,
미식 기준 값이 다른 기기로 넘어가지 않는다.

1. Xcode 에서 디버그 빌드를 실행 인자 `-cloudKitSchemaWarmup` 으로 띄운다(iCloud 에 로그인한 기기 · 시뮬레이터).
   개인 DB 에 `CD_Visit` 의 `CD_gourmet…` 네 필드와 `CD_Restaurant` 의 `CD_sharedReviewID` 가,
   공개 DB 에 `RegularReview` · `ReviewReport` 가 개발 환경에 생긴다.
2. CloudKit 콘솔(개발 환경) ▸ Indexes ▸ `RegularReview`: `postedAt` 에 QUERYABLE 과 SORTABLE 을 단다.
   `ReviewReport`: `kind` 에 QUERYABLE 을 단다 (세 사람 신고를 세는 데 쓴다).
3. Security Roles 가 기본값인지 본다: `RegularReview` · `ReviewReport` 모두 World 읽기, Authenticated 만들기, Creator 쓰기.
4. Security Roles 에 `Moderator` 역할을 새로 만들고 `RegularReview` 에 읽기 · 쓰기를 준다.
5. Deploy Schema Changes 로 운영에 올린다.
6. **운영 환경**에서 개발자 계정에 `Moderator` 를 준다: 개발자 iPhone 의 스토어 빌드(TestFlight)로 한 번 열어
   `Users` 에 내 레코드가 생기게 한 뒤, 콘솔(Production) ▸ Records ▸ `Users` 에서 그 레코드를 열어 역할에 `Moderator` 를 더한다.
   개발 환경에서도 시험하려면 개발 환경 `Users` 에도 같은 일을 한다.
7. 스토어 빌드(TestFlight)에서 후기 올리기 · 읽기 · 신고 · 관리자 내리기가 되는지 본다.

## 아직 안 한 것

- 내 주변 후기 먼저 보기 (로드맵 `reviews.nearby`). `location` 필드는 이미 올리고 있다.
- 서비스 · 분위기 · 가성비. 넣는다면 음식 점수와 따로.
- 되풀이해 규칙을 어기는 사람을 서버에서 막는 장치. 지금은 글을 지우는 것까지다.
